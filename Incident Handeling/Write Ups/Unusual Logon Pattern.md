# Unusual sequence of failed logons
## Incident Analysis: External Brute‑Force Activity Against an Internet‑Facing RDP Host

### Alert Trigger and Initial Detection
A security alert was generated by Microsoft Defender for Endpoint indicating an unusual sequence of failed authentication attempts against a Windows Server host (xx‑test). The alert was triggered due to repeated remote logon failures originating from an external IP address with a known malicious reputation.
The affected system was confirmed to be internet‑facing, and similar alerts involving this host had been observed previously. This indicated recurring exposure rather than a one‑time or accidental event.

### Triage and Investigation Performed
The primary goal of the triage was to determine whether the observed activity resulted in a successful authentication or system compromise, and to identify which service was being targeted.

#### Authentication Review
The following authentication checks were performed:

##### Endpoint authentication logs were reviewed.
All observed logon attempts resulted in failed authentication events.

```kql
DeviceLogonEvents
| where DeviceName == "HOST" and RemoteIP == "IP"
```

No successful logons were identified.
This confirmed that no account compromise occurred during the observed activity.

No evidence of interactive user sessions, lateral movement, persistence mechanisms, or follow‑up malicious activity was observed.

##### Service and Protocol Analysis
Further investigation focused on identifying the exposed service responsible for the alert.

```kql
search "IP"
```

```kql
DeviceEvents
| where * == "IP"
```

Endpoint telemetry showed repeated Remote Desktop connection attempts against the host.
Network telemetry confirmed multiple inbound connections accepted by the system.
All inbound connections were associated with the Windows Terminal Services process, confirming the use of Remote Desktop Protocol (RDP).

```kql
DeviceNetworkEvents
| where * contains "IP"
```

This established that the Remote Desktop service was the targeted attack surface.

##### Correlation and Behavioral Assessment
Correlating authentication, network, and service telemetry revealed the following consistent pattern:

Using DeviceNetworkEvents and DeviceEvents

- External systems initiated connections to the Remote Desktop service.
- The service accepted inbound TCP connections.
- Authentication attempts were made repeatedly.
- All authentication attempts failed.
- No Remote Desktop sessions were successfully established.

This behavior is consistent with automated external scanning and brute‑force attempts against an internet‑facing RDP service.
At the time of investigation, Network Level Authentication (NLA) was not enabled on the host. Without NLA, the full RDP authentication flow is exposed, making the service more susceptible to repeated credential‑guessing attempts and increasing alert frequency.

### Research and Validation
To validate the findings, additional contextual research was performed as part of the investigation:

Confirmed that internet‑facing RDP services are commonly and continuously targeted by automated attack infrastructure, regardless of whether credentials are successful.
Verified that security alerts are expected behavior when repeated failed RDP authentication attempts are observed on exposed systems.
Reviewed Microsoft security guidance confirming that:

Direct internet‑facing RDP is not recommended
Network Level Authentication reduces exposure, but does not eliminate inbound connection attempts
Additional controls (such as gateways, VPNs, or IP‑based restrictions) are required to fully mitigate this behavior
This confirmed that the alert represented expected defensive detection, not a false positive or internal misconfiguration.

### Conclusion

The activity originated from an external source with a malicious reputation.
The affected system (xx‑test) was directly exposed to the internet.
The Remote Desktop service was repeatedly targeted.
All authentication attempts failed.
No evidence of compromise or successful access was identified.

The activity is assessed as external hostile scanning and brute‑force attempts with no impact.

### Recommendations
Based on the findings, the following recommendations were provided:

- Review whether the affected system must remain internet‑facing and continuously accessible.
- Enable Network Level Authentication (NLA) to reduce RDP exposure and limit pre‑authentication attack surface.
- Apply additional hardening measures in line with Microsoft security best practices, such as:
  - Avoiding direct internet‑facing RDP
  - Using a remote access gateway or VPN
  - Restricting inbound access by IP address where possible

### Follow‑Up
The case was discussed with the appropriate operational teams, and follow‑up actions were planned to determine whether the system’s exposure was required and to align on appropriate remediation steps.

#### Why this case is relevant
This case illustrates that:

- Security alerts do not require a breach to be valid
- Internet‑facing services will attract hostile attention
- MxDR can mean more than just detect and response. It can also be a valid partner to discuss and evaluate security findings.
