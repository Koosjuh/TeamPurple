# Unusual Sequence of Failed Logons ## Incident Analysis: External Activity Against an Internet-Facing RDP Host 

### Alert Trigger and Initial Detection 
A security alert was generated by Microsoft Defender for Endpoint indicating an unusual sequence of failed authentication attempts against a Windows Server host (xx-test). The alert was triggered due to repeated remote logon failures originating from external IP addresses with known malicious reputation. The affected system was confirmed to be internet-facing. Similar alerts involving this host had been observed previously, indicating recurring exposure rather than a one-time event. 

--- 

## Triage and Investigation Performed 
The primary objective of the investigation was to determine: 

- Whether any authentication attempt succeeded
- Whether a Remote Desktop session was successfully established
- Whether the activity resulted in compromise
- Which service was being targeted 

--- 
## IP Reputation Review 
The following sources were used to validate source IP reputation: 

- https://scamalytics.com/
- https://www.abuseipdb.com/
- https://spur.us/
  
The IPs were identified as malicious infrastructure, likely associated with automated attack hosting rather than legitimate VPN providers.

--- 

## Authentication Review Endpoint authentication logs were reviewed to determine whether any successful authentication occurred.

```kql
DeviceLogonEvents
| where DeviceName == "HOST" and RemoteIP == "IP"
```

All observed authentication attempts resulted in: - ActionType = LogonFailed - FailureReason = InvalidUserNameOrPassword - LogonType = Network - Protocol = NTLM No successful logons were identified. No LogonType = RemoteInteractive events were observed for the investigated IPs. This confirms: - No successful RDP authentication - No interactive Remote Desktop session - No account compromise during the observed timeframe No evidence of lateral movement, persistence, privilege escalation, or follow-up malicious activity was identified in DeviceTimeline. RDP accepted inbound connections on TCP/3389. Authentication telemetry for the same source IPs showed only failed Network logons using NTLM and no RemoteInteractive logons, indicating that connection attempts did not progress to a successful interactive RDP session. --- ## Service and Protocol Analysis To identify the targeted service, network telemetry was reviewed.

```kql
search "IP"
```

I started with a broad pivot on the source IP across Defender advanced hunting to identify all related telemetry, then narrowed the scope to the most relevant tables: DeviceNetworkEvents for inbound connection evidence and DeviceLogonEvents for authentication outcomes. This approach ensures coverage (no missed artifacts) while keeping conclusions grounded in the most authoritative event types for network vs. authentication.

```kql
DeviceEvents
| where * == "IP"
```

```kql
DeviceNetworkEvents
| where * contains "IP"
```

Results showed repeated: 
- ActionType = InboundConnectionAccepted
- Protocol = Tcp
- LocalPort = 3389
- Initiating process: svchost.exe -k termsvcs -s TermService

This confirms the Windows Remote Desktop Service (TermService) accepted inbound TCP connections on port 3389. 

Example validated event: 
- LocalPort = 3389
- Protocol = Tcp
- ActionType = InboundConnectionAccepted
- InitiatingProcessFileName = svchost.exe
- InitiatingProcessCommandLine = svchost.exe -k termsvcs -s TermService

This establishes that RDP was internet-reachable and accepting inbound connections.

## Correlation and Behavioral Assessment 

Additional correlation was performed to determine whether RDP connections progressed to interactive authentication.

```kql
let Lookback = 14d;
let TargetDevice = "xx-test";
let SuspectIPs = dynamic(["IP","IP","IP"]);
  DeviceLogonEvents
    | where Timestamp >= ago(Lookback)
    | where DeviceName == TargetDevice
    | where RemoteIP in (SuspectIPs)
    | summarize Count=count(), FirstSeen=min(Timestamp), LastSeen=max(Timestamp)
      by RemoteIP, LogonType, ActionType, Protocol, FailureReason
    | order by RemoteIP asc
```

Findings: 
- Only LogonType = Network events were observed.
- No LogonType = RemoteInteractive events were detected.
- Authentication attempts used NTLM.
- All authentication attempts failed.
- Additionally, RDP connection activity was reviewed:

```kql
DeviceNetworkEvents
| where DeviceName == "xx-test"
| where LocalPort == 3389
```

Multiple inbound TCP connections were accepted from the external IPs. However: 
- No corresponding RemoteInteractive logon attempts were observed.
- No successful authentication events were present.
- No evidence of interactive desktop session creation was identified in Defender telemetry.

--- 

## Technical Interpretation 

The observed behavior indicates: 
- External systems initiated connections to TCP 3389.
- The RDP service accepted inbound TCP handshakes.
- Separate NTLM network authentication attempts were performed.
- All authentication attempts failed.
- No evidence supports that an interactive RDP session reached the Windows logon UI.

Although Network Level Authentication (NLA) was confirmed not to be enabled on the host, the telemetry does not demonstrate that attackers progressed to interactive credential submission over RDP. The pattern is consistent with: 
- Automated RDP port scanning - Credential spraying over NTLM
- Automated brute-force infrastructure

The activity reflects background internet attack noise targeting exposed services. The authentication failures were recorded as LogonType = Network (Windows Logon Type 3) using NTLM. Interactive RDP logons generate LogonType = RemoteInteractive (Type 10). No Type 10 events were observed for the investigated IPs. Network telemetry confirmed that the only inbound accepted service from these IPs was TCP 3389 (Remote Desktop). No inbound connections to SMB (445) or other NTLM-enabled services were observed.

```kql
DeviceNetworkEvents
| where Timestamp >= ago(14d)
| where DeviceName == "xx-test"
| where RemoteIP in ("IP","IP","IP")
| where ActionType == "InboundConnectionAccepted"
| summarize count() by LocalPort
| order by LocalPort asc
```

This indicates that the NTLM authentication failures occurred during the RDP authentication negotiation phase prior to interactive session creation, rather than via SMB or other services. No evidence was found that authentication progressed to an interactive RDP desktop session. 

--- 

## Research and Validation

Industry guidance confirms: 
- Internet-facing RDP services are continuously targeted by automated attack infrastructure.
- Repeated failed authentication attempts are expected when RDP is exposed.
- Network Level Authentication reduces pre-authentication exposure.
- Direct internet-facing RDP is not recommended.
- Additional controls (VPN, RDP Gateway, IP restriction) are required for proper hardening.

This confirms the alert represented legitimate detection of hostile activity, not a false positive. 

--- 

## Conclusion 
- The activity originated from external IP addresses with malicious reputation.
- The affected system (xx-test) was directly exposed to the internet.
- The Remote Desktop service accepted inbound TCP connections.
- NTLM authentication attempts were observed.
- All authentication attempts failed.
- No successful logons were identified.
- No interactive RDP sessions were confirmed.
- No evidence of compromise was observed.
- The activity is assessed as automated hostile scanning and credential brute-force attempts with no impact.

--- 

## Recommendations 
- Review whether the system must remain directly internet-facing.
- Enable Network Level Authentication (NLA).
- Avoid direct exposure of RDP to the internet.
- Implement VPN or Remote Desktop Gateway.
- Restrict inbound access by IP address where feasible.

--- 

## Follow-Up 
The findings were discussed with the responsible operational teams. Follow-up actions were planned to evaluate exposure necessity and implement appropriate hardening measures.

## Why This Case Is Relevant 
This case demonstrates that: 
- Security alerts do not require successful compromise to be valid.
- Internet-facing services will attract continuous hostile attention.
- Detection and response includes exposure validation and hardening guidance, not only breach response.

  ### Triage Conclusion
The device xx-test is directly exposed to the internet with TCP 3389 (Remote Desktop) accessible externally. Multiple external IP addresses with malicious reputation performed automated scanning and credential brute-force attempts. Inbound RDP TCP connections were accepted by the Windows Terminal Services process. All observed authentication attempts failed. Only LogonType = Network NTLM failures were recorded. No RemoteInteractive logon attempts or successful authentications were identified. No evidence of interactive RDP session establishment or compromise was found. The activity is assessed as automated hostile scanning against an exposed RDP service with no impact to the system. During our upcoming bi-monthly Threat Vulnerability Management session, this configuration will be reviewed to assess:
- The functional purpose of the system.
- The business requirement for direct internet exposure.
- Whether continuous 24/7 accessibility is necessary.
- The appropriateness of enabling Network Level Authentication (NLA).
  - Additional hardening options such as access restriction, gateway usage, or removal of direct RDP exposure. The objective will be to determine whether the current exposure aligns with operational requirements and security best practices.
